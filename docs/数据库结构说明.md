# GEO 系统数据库结构说明（V1.0 + 审核修正）

> 维护人：C（数据库与交付）。表结构变更一律走 Alembic 迁移脚本，评审后合入 `main`。
> 本文件描述设计意图；**以库内真实结构为准的逐表核对见 [表结构核对表.md](表结构核对表.md)**（由 `backend/scripts/audit_schema.py` 生成），建库 DDL 见 [数据库DDL.sql](数据库DDL.sql)。

## 一、总体结构

- 数据库：PostgreSQL 16（Docker `postgres:16`，本机映射 5433，原生 5432 被已有实例占用）。
- 表：43 张 = **35 张带 `project_id` 的项目业务表（含 `import_batches`）+ 7 张系统级表（`users`、`roles`、`permissions`、`role_permissions`、`projects`、`ai_engines`、`ai_engine_entries`）+ 1 张迁移元数据表（`alembic_version`）**。三类互斥，合计 43；`docs/表结构核对表.md` 按此口径由库直接生成。
- 实测（2026-11-17，库内真实结构）：137 索引、108 外键、39 条表级 CHECK（枚举约束 + 角色/能力码取值 + outbox 项目/系统边界；`pg_constraint contype='c'` 总数为 39，全部挂在表上）。
- 主键：全部 `UUID`，由**应用侧生成**（`uuid4()`），数据库无 `gen_random_uuid()` 默认值，接口可直接透传主键。
- 枚举：统一存 `VARCHAR + CHECK`（`native_enum=False, create_constraint=True`），扩值只改代码不改类型。
- 时间：`timestamptz`，服务端默认 `now()`，`updated_at` 由 ORM `onupdate` 维护。

## 二、项目隔离规则

1. 除白名单表外，**所有业务表必须带 `project_id NOT NULL`**，外键指向 `projects.id`，`ON DELETE RESTRICT`。
2. 系统级表白名单（仅 7 张，新增必须评审）：
   - `users`（账号）、`roles`（角色字典）、`permissions`（能力码）、`role_permissions`（角色—能力映射）、`projects`（项目注册表）、`ai_engines`（引擎目录）、`ai_engine_entries`（引擎入口目录）。
   - `audit_logs.project_id` 允许为空，仅用于记录系统级操作；项目内操作必须写入项目 id。
3. 权限判断顺序：登录身份 → `project_members` 校验该项目授权 → 角色能力（`role_permissions`）→ 才允许读写。**不信任前端传来的 `project_id`**；判定在 `backend/app/services/access.py`，HTTP 适配在 `backend/app/api/deps.py`，能力矩阵唯一事实来源在 `backend/app/core/permissions.py`。
4. 单条记录读取一律带 `project_id` 条件（`app/services/project_scope.py`），查不到按越权处理，不暴露记录是否存在。
5. 异步链路必须带项目标识：`outbox_events` 表有 `project_id`，事件 `payload` 里也必须带同名项目键，Worker 执行前用 `app/core/task_guard.py` 重新落库核对。
6. 缓存键、证据文件路径、导出任务文件名都必须带项目标识。
7. `sys_admin` 只有一条判定链：**系统级权限只认 `users.is_system_admin` + 能力矩阵**。`roles.sys_admin` 只是字典行/能力映射载体，不参与项目成员授权；`project_members.role_id` 指向它时按无效授权拒绝（`sys_admin_role_not_assignable`）。库层无法跨表 CHECK，故由 `app/services/access.py` 服务端 guard + `tests/test_rbac_acceptance.py::test_10` 兜底；直连写库需 DBA 遵守同一规则。
8. outbox 事件的项目边界由库层 CHECK 兜底：`project_id IS NOT NULL OR topic LIKE 'system.%'`。项目级事件必须带项目 id（`emit_event` 还要求 payload 内项目键一致）；系统级事件（`system.engine.catalog.sync`、`system.permission.matrix.sync`）`project_id` 为空、topic 必须 `system.` 前缀，走 `emit_system_event`。系统级变更同时写 `audit_logs`。

## 三、模块与表

下表中“项目级”表的 `project_id` 均已在库内实测为 `NOT NULL` + `RESTRICT`。

### 3.1 系统与权限

| `roles` | 系统级 | code(唯一)、name | `roles_code_check`：sys_admin/project_admin/editor/reviewer/viewer/lead_ops（历史 `admin` 已就地改名 `project_admin`）。**`sys_admin` 这行只用于能力映射与字典展示，禁止写进 `project_members`** |

| `role_permissions` | 系统级 | role_id、permission_id | `uq_role_permissions_role_permission`，双外键指向 `roles` / `permissions` |

| `audit_logs` | 项目级（可为空） | actor_id、action、target_type/target_id、payload(JSONB) | `ix_audit_logs_project_created`、`ix_audit_logs_target`；`project_id` 实测 **is_nullable=YES**，外键 `fk_audit_logs_project_id_projects` 为 `ON DELETE SET NULL`。项目级审计按 `audit.read` 限本项目；`project_id IS NULL` 的系统级审计只有 `is_system_admin` 可查 |

| `metric_definitions` | 项目级 | code + rule_version + formula + effective_from | `uq_metric_definitions_project_code_version`（**口径是项目级的，project_id 已改 NOT NULL**） |
| `import_batches` | 项目级 | source_system、mapping_version、status、counts(JSONB) | `ix_import_batches_project_started`；历史数据迁移用，见 [历史数据迁移方案.md](历史数据迁移方案.md) |

#### 3.1.1 角色—能力矩阵（25 个能力码，59 条映射）

能力码：`project.create`、`project.read`、`project.member.manage`、`engine.manage`、`question.read`、`question.write`、`monitoring.read`、`monitoring.execute`、`evidence.read`、`evidence.review`、`content.read`、`content.write`、`content.review`、`publish.read`、`publish.execute`、`channel.read`、`channel.write`、`lead.read`、`lead.write`、`stats.read`、`export.data`、`audit.read`、`competitor.write`、`metric.manage`、`engine.verify`。

| 角色 | 能力数 | 关键边界 |
| --- | --- | --- |
| `sys_admin` | 2 | 只有 `project.create` + `engine.manage`；不默认读写项目业务数据，要读写必须先被加入项目并分配业务角色 |
| `project_admin` | 18 | 成员管理 + 全项目读 + `content.review` / `evidence.review` + `channel.write` + `competitor.write` / `metric.manage` / `engine.verify` + `export.data` / `audit.read`；无 `content.write`、无 `publish.execute`、无建项目/引擎能力 |
| `editor` | 17 | 题库/监测执行/内容母稿与版本/发布执行/渠道台账/竞品台账/指标口径 + `engine.verify`（测试连接）+ 导出；无审批、无成员管理、无 `lead.read` |
| `reviewer` | 9 | 审批与证据复核 + 读；无 `content.write`（改正文 403）、无发布、无成员管理 |
| `viewer` | 10 | 全项目读 + `export.data`（导出必写审计）；所有写接口 403 |
| `lead_ops` | 3 | `project.read` + `lead.read` + `lead.write`；监测/证据/内容/发布/渠道接口一律 403 |

授予约束（服务端强制，不依赖前端）：可授予角色白名单只有 `editor` / `reviewer` / `viewer` / `lead_ops`；`project_admin` 与 `sys_admin` 不可被授予；管理类能力（`project.create`、`engine.manage`、`project.member.manage`）不得随角色转授。实现见 `app/core/permissions.py::can_grant` 与 `app/services/access.py::ensure_can_grant`。

`review_result` 与 `brand_mentioned` 分开存，人工复核不覆盖自动识别值。

## 五、迁移工作流

```powershell
# 在仓库根目录执行（alembic.ini 位于根目录，脚本目录 %(here)s/migrations）
.\backend\.venv\Scripts\alembic.exe upgrade head
.\backend\.venv\Scripts\alembic.exe current
.\backend\.venv\Scripts\alembic.exe check            # 必须返回 No new upgrade operations
.\backend\.venv\Scripts\alembic.exe revision --autogenerate -m "描述"
```

迁移链：

| revision | 内容 |
| --- | --- |
| `6244e674a083` | baseline（空库握手） |
| `460052748386` | V1.0 核心结构，33 张业务表；含手写修正 `fk_content_items_current_version` |
| `482fc59c5212` | 审核修正：`users.is_system_admin`、`metric_definitions.project_id` 收紧为 NOT NULL、`import_batches` 与 `import_batch_id`、3 个组合索引 |
| `3f9c1d2e4b57` | RBAC 六角色与权限矩阵 |
| `8d1e2f3a4b5c` | outbox 系统级事件允许 `project_id` 为空 |
| `32e8750970c2` | 线索归因：`leads` 增加题目/渠道/引擎外键、落地页与 UTM 字段，3 个组合索引 |
| `882cf6d84462` | 基线轮次唯一：`monitoring_rounds` 增加 `project_id` 部分唯一索引，仅约束 `is_baseline IS TRUE` 的行 |

规则：

1. 只改 `backend/app/models/`，然后 autogenerate，不手写建表 SQL。
2. 生成后逐项检查索引、唯一约束、`ondelete`、枚举 CHECK。
3. `use_alter` 循环外键 autogenerate 会漏，需手工补 `op.create_foreign_key`（当前只有 `content_items.current_version_id`）。
4. 迁移必须可回滚：`downgrade base` → `upgrade head` 能重建全库（已实测）；downgrade 里的 `drop_constraint` 对“可能不存在”的约束要用 `DROP CONSTRAINT IF EXISTS`。
5. 结构变更由 C 评审后合入 `main`，合入前必须跑 `alembic check` 与 `pytest`。
