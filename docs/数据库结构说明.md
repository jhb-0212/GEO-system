# GEO 系统数据库结构说明（V1.0）

> 维护人：C（数据库与交付）。表结构变更一律走 Alembic 迁移脚本，变更需评审后合入 `main`。

## 一、总体结构

- 数据库：PostgreSQL 16（Docker 镜像 `postgres:16`，本机映射端口 5433，原生 5432 被已有实例占用）。
- 业务表 33 张 + `alembic_version`。当前实测：96 个索引、80 个外键、32 个枚举 CHECK 约束。
- 主键：全部业务表 UUID（`gen_random_uuid()` 应用侧生成），便于导出、跨库迁移与接口透传。
- 枚举：统一落库为 `VARCHAR + CHECK`，不用 PG 原生 enum，扩值只改代码不改类型。
- 时间字段：`timestamptz`，服务端默认 `now()`；`updated_at` 由 ORM `onupdate` 维护。

## 二、项目隔离规则

1. 所有**项目业务表**必须带 `project_id`，外键指向 `projects.id`，`ON DELETE RESTRICT`（防误删项目连带清空数据）。
2. 系统级参考数据只有两张表不带 `project_id`：`ai_engines`、`ai_engine_entries`（引擎目录对所有项目一致，采样记录才归属项目）。
3. 权限判定顺序：登录身份 → `project_members` 校验该项目授权 → 角色权限 → 才允许读写。**不信任前端传来的 `project_id`**。
4. 缓存键、队列消息、证据文件路径、导出任务都必须携带项目标识；后台任务执行前重新校验归属。
5. `audit_logs.project_id` 允许为空（记录系统级操作），但项目内操作必须写入。

## 三、模块与表

### 3.1 系统与权限

| 表 | 关键字段 | 关键约束 / 索引 |
| --- | --- | --- |
| `users` | username(唯一)、email、display_name、password_hash、is_active | `uq_users_username`、`uq_users_email` |
| `roles` | code(唯一)、name | code 覆盖 admin/editor/reviewer/viewer/lead_ops |
| `projects` | code(唯一)、name、status、timezone | `uq_projects_code` |
| `project_members` | project_id + user_id + role_id | `uq_project_members_project_user`；`ix_project_members_user` |
| `audit_logs` | actor_id、action、target_type/target_id、payload(JSONB) | `ix_audit_logs_project_created`、`ix_audit_logs_target` |
| `outbox_events` | topic、payload(JSONB)、status | `ix_outbox_events_status_created`；业务记录与入队同事务 |
| `metric_definitions` | code + rule_version + formula | `uq_metric_definitions_project_code_version` |

### 3.2 题库与关键词

| 表 | 关键字段 | 关键约束 |
| --- | --- | --- |
| `keywords` | name、category、priority | `uq_keywords_project_name` |
| `questions` | code、title、question_type(brand/general)、status、current_version_no | `uq_questions_project_code`、`ix_questions_project_type_status` |
| `question_versions` | question_id、version_no、text | `uq_question_versions_question_version`；版本只增不改 |

监测任务只引用 `question_versions.id`，所以后续改题目不会改变历史记录含义。

### 3.3 AI 引擎目录（系统级）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `ai_engines` | code、name、vendor、supports_search、supports_citation、last_verified_at | 首期 4 个：豆包、腾讯元宝、DeepSeek、百度文心 |
| `ai_engine_entries` | engine_id、entry_type(web_user/app_user/api/app_search)、entry_url | `uq_ai_engine_entries_engine_type_name`；同厂商多入口分开记录 |

### 3.4 GEO 监测与证据

| 表 | 关键字段 | 关键约束 |
| --- | --- | --- |
| `monitoring_rounds` | seq、name、is_baseline、status | `uq_monitoring_rounds_project_seq` |
| `monitoring_tasks` | round_id、question_version_id、engine_entry_id、sampling_no、sampling_mode、status | `uq_monitoring_tasks_round_question_entry_sampling`（轮次+问题版本+引擎入口+采样序号） |
| `monitoring_samples` | task_id、attempt_no、status、raw_answer、brand_mentioned、failure_code、review_* | `uq_monitoring_samples_task_attempt` |
| `monitoring_citations` | raw_url、normalized_url、domain、channel_id、is_brand_related、review_status | `ix_monitoring_citations_project_domain` |
| `evidence_files` | storage_key、file_type、checksum、byte_size | 文件本体在对象存储，库里只存元信息 |

采样状态机：`pending → running → hit / miss / failed / manual_review`。
`failure_code` 覆盖 login_blocked / timeout / access_blocked / captcha / rate_limited / other，**失败样本不进有效分母**。
`review_result` 与 `brand_mentioned` 分开存，人工复核结果不覆盖自动识别值。

### 3.7 发布管理

| 表 | 关键字段 | 关键约束 |
| --- | --- | --- |

## 四、迁移工作流

```powershell
# 在仓库根目录执行（alembic.ini 在这里，脚本目录 %(here)s/migrations）
.\backend\.venv\Scripts\alembic.exe upgrade head      # 应用迁移
.\backend\.venv\Scripts\alembic.exe current           # 当前版本
.\backend\.venv\Scripts\alembic.exe check             # 模型与库是否漂移（必须返回 No new upgrade operations）
.\backend\.venv\Scripts\alembic.exe revision --autogenerate -m "描述"   # 生成新迁移
```

规则：

1. 改表只改 `backend/app/models/`，再 autogenerate，不手写建表 SQL。
2. 生成后必须打开脚本检查：索引、唯一约束、`ondelete`、枚举 CHECK 是否齐全。
3. `use_alter` 的循环外键（目前只有 `content_items.current_version_id`）autogenerate 会漏，需要手工补 `op.create_foreign_key`。
4. 迁移必须可回滚：`downgrade base` 再 `upgrade head` 能重建全库（已实测通过）。
5. 结构变更由 C 评审后合入 `main`。
