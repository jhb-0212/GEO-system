# 历史数据迁移方案

> 责任人：C。范围：旧本地存储中的题库、渠道台账、线索，以及模拟状态数据。目标库：`geo`（PostgreSQL 16）。

## 一、迁移原则

1. **批次化**：每次导入建一条 `import_batches` 记录，批次 id 即旧数据的身份证。
2. **可核对**：批次里记录源行数、逐表 imported / skipped / failed、导入前后行数与增量。
3. **可回滚**：按批次 id 删除即可撤销，回滚动作本身写审计，可追溯。
4. **不覆盖**：按目表唯一键去重，已存在的数据计入 skipped，不修改既有业务内容。
5. **先试跑**：正式导入前必须 `--dry-run`，确认映射与去重结果。

## 二、批次机制

新增表 `import_batches`（迁移 `482fc59c5212`）：

| 字段 | 含义 |
| --- | --- |
| `project_id` | 归属项目，`ON DELETE RESTRICT` |
| `source_system` | 来源系统标识，如 `legacy_local` |
| `mapping_version` | 映射版本，当前 `v1`，映射变更必须升版本 |
| `status` | pending / running / completed / failed / rolled_back |
| `counts` | JSONB：`source_rows`、`per_table`、`before`、`after`、`delta` |
| `started_at` / `finished_at` | 批次时间窗 |
| `rollback_note` | 回滚说明与删除计数 |
| `created_by` | 执行人（脚本执行可空） |

以下目标表带 `import_batch_id`（`ON DELETE SET NULL`）用于标记旧数据来源：
`questions`、`question_versions`、`content_items`、`content_versions`、`channels`、`leads`。

**旧数据识别规则**：`import_batch_id IS NOT NULL` 即为导入数据；同一批次内的行永远可整批撤销。业务查询与看板不按该字段过滤，它只用于溯源与回滚。

## 三、字段映射表（mapping_version = v1）

| 源文件 | 目标表 | 源字段 → 目标字段 | 必填 | 去重键 |
| --- | --- | --- | --- | --- |
| `questions.csv` | `questions` | `code`→`code`、`question_text`→`title`、`qtype`→`question_type`、`audience`→`audience` | code、title | `project_id + code` |
| `channels.csv` | `channels` | `code`→`code`、`channel_name`→`name`、`category`→`category`、`domain`→`primary_domain` | code、name | `project_id + code` |
| `leads.csv` | `leads` | `contact_name`→`contact_name`、`phone`→`contact_phone`、`wechat`→`contact_wechat`、`course`→`interested_course`、`source`→`lead_source`、`remark`→`note` | contact_name | 手机号或微信号 |

字段转换规则：

- `qtype`：`general`/空/“通用” → `general`，其余 → `brand`。
- `category`：取 `ChannelCategory` 枚举值，无法识别时置 `content_platform` 并在核对阶段人工确认。
- 导入的题目一律 `status=draft`、`current_version_no=1`，不自动生成正式版本；确认问法后再追加 v2。
- 导入的渠道一律 `status=candidate`，准入需人工确认。

## 四、执行步骤

```powershell
# 0) 结构就绪
.\backend\.venv\Scripts\alembic.exe upgrade head

# 1) 试跑，不写库
cd backend
.\.venv\Scripts\python.exe scripts\import_legacy.py --source scripts\legacy_samples --project-code gz-base --dry-run

# 2) 正式导入（记下批次 id）
.\.venv\Scripts\python.exe scripts\import_legacy.py --source scripts\legacy_samples --project-code gz-base

# 3) 核对（批次 counts 与库内实际行数）
docker exec geo-postgres psql -U geo -d geo -c "select counts from import_batches order by created_at desc limit 1;"

# 4) 需要撤销时按批次回滚
.\.venv\Scripts\python.exe scripts\import_legacy.py --rollback <batch_id>
```

## 五、数量核对口径

- 源行数 = imported + skipped + failed（脚本直接打印等式，任一不等即视为异常）。
- 表增量 = after − before，必须等于该表 imported。
- 核对结果写入批次 `counts`，并同步写 `audit_logs`（action = `legacy_import`）。

## 六、回滚与追溯

- 回滚按批次删除，顺序为 `leads` → `questions` → `channels`（子表依赖先删）。
- 回滚后批次状态置 `rolled_back`，`rollback_note` 记录删除数与前后行数，并写审计 `legacy_import_rollback`。
- 常见边界：若导入的题目已被引用（生成监测任务），删除会受外键约束阻止；此时应先处理引用，或改为保留数据、只把批次标记为回滚完成并说明原因。

## 七、本轮演练结果（真实输出）

```

正式导入：批次 6b2f4bd6-5255-4fd7-ac70-2d5964d6e2ee

回滚：删除 {'questions': 2, 'channels': 2, 'leads': 2}；行数 {questions: 8, channels: 41, leads: 2} -> {questions: 6, channels: 39, leads: 0}
```

源数据用 `backend/scripts/legacy_samples/` 的样例 CSV 代替（旧系统未交付真实导出），映射与去重逻辑已验证。

## 八、待业务提供的输入

1. 旧系统真实导出文件（或含真实数据的 CSV 样本），用于确认字段命名与脏数据形态。
2. “模拟状态数据”是否需要入库：如需，需定义目标表与映射（当前方案未覆盖，避免污染监测统计口径）。
3. 旧数据的日期字段是否要保留原时间：当前方案导入记录使用导入时刻，若需保留原始提交时间，需为新字段加迁移。
