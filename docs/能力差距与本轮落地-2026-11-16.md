## 本轮具体落地

### 1. 跨实体 trace 后端

`backend/app/services/trace_chain.py`：

- 保留 `trace_for_content_version()`：内容版本 → 唯一监测 trace，多 trace 返回 `None`，不猜。
- 新增 `trace_detail(db, project_id, trace_id)`：只读查询，返回：
  - `rounds`：轮次；
  - `tasks`：任务 + 问题/版本/引擎/入口；
  - `samples`：样本 + 状态、品牌提及、失败码、延迟、token、费用、网关版本；
  - `citations`：引用 + 域名、品牌相关、used/cited、复核状态；
  - `content_versions`：只纳入通过 `content_version_citations` 真正引用本 trace 引用的版本；
  - `publish_tasks`：按 `trace_id` 或版本关联；
  - `counts`：六类节点计数。
- 没有任何节点时返回 `found=false` + 空数组，不补假节点。

接口：`GET /api/v1/projects/{project_id}/monitoring/traces/{trace_id}`，权限 `monitoring.read`，响应 `Envelope[TraceChainData]`。

### 2. 跨实体 trace 前端

`frontend/components/diagnostics-workspace.tsx` 在“内部排障”页新增“跨实体 trace 链路”：

- 输入 trace_id，回车或点“查链路”；
- 四列展示任务、样本、引用、内容版本/发布；
- 顶部显示六类节点计数；
- `found=false` 时明确提示当前项目下没有节点，不显示空白表格。

代理路由：`frontend/app/internal/workbench/data/route.ts` 的 `kind=trace`，校验 trace_id 只允许 `A-Za-z0-9_-`、4–64 位，再转发到后端。

### 3. 情感与品牌位次

`backend/app/services/stats.py::geo_overview` 增量：

- `sentiment`：只取包含品牌词的句子，用正/负词典净分，归类 `positive/neutral/negative`；未出现品牌句记 `not_mentioned`，不进正面率分母；
- `brand_position`：品牌词首次出现位置之前有几个竞品出现，再 `+1`；只统计品牌被提及的有效回答；
- `sov` 口径不变：有品牌提及的有效回答 /（品牌提及 + 竞品提及的有效回答）。

返回新增：

```json
{
  "sentiment": {
    "positive": 1,
    "neutral": 0,
    "negative": 0,
    "not_mentioned": 0,
    "positive_rate": 1.0,
    "average_score": 2.0
  },
  "brand_position": {
    "sample_count": 1,
    "average_rank": 1.0,
    "top1_rate": 1.0
  }
}
```

统计总览新增四张卡：竞品份额 SOV、品牌正向率、平均提及位次、首位提及率；下面单列情感分布与位次样本数。

### 4. 边界与未做

- **情感是规则词典，不是模型判定**。否定词、反讽、长句转折都可能判错，当前只用于内部趋势参考，不能直接对外当结论。
- **品牌位次按文本首次出现顺序**，不解析引擎自带排名结构；不同引擎回答长度差异大，位次只在同口径下横向比较。
- **query fan-out 未实现**。当前 `AnswerPayload` 没有 `search_queries` 字段，库里也没有真实检索 query 留存。只在适配器真能返回 query 后再开，且只对 `supports_search=True` 的入口开放。
- **真实引擎覆盖仍是 1 条**。fallback 逻辑已实现，但没有第二个可用入口可验证，不能说“多引擎 fallback 已验收”。
- 前端 e2e、浏览器视觉验收未做；本轮只到 tsc / eslint / build 与 HTTP 检查。
