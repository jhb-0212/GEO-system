# 工作台页面可见性与权限分级方案

> 状态：P0–P3 已实施；浏览器 E2E 覆盖 5 个真实账号（系统管理员兼项目管理员 / 编辑 / 审核 / 只读 / 招生），纯 `sys_admin` 账号待补  
> 日期：2026-11-17（实施完成 2026-11-18）  
> 范围：`frontend/components/workbench-app.tsx` 导航与页面展示、`frontend/lib/workbench/visibility.ts` 可见性判断、`frontend/app/internal/workbench/route.ts` 快照权限、后端对应接口门禁与字段裁剪

## 1. 结论

要分，但**按角色/能力码分，不按账号逐个隐藏**。

分三层，不要混在一起：

1. **页面可见性**：这个账号是否应该看到这个菜单/页面。
2. **操作可见性**：进页面后，哪些按钮可点（写、审核、执行、导出）。
3. **字段可见性**：同一页面里，哪些字段对哪些角色展示（入口 URL、credential_ref、失败 trace、手机号等）。

原则：

- 后端接口是唯一权限事实源；前端隐藏只负责减少误点和 403。
- 默认拒绝；有明确读取能力才展示。
- 系统管理员只自动拥有“系统级页面”，不自动获得项目业务页面权限。
- 全局资源（AI 平台目录）按“全局能力”判断，不能只看当前项目的角色。

## 2. 现状问题

### 2.1 已确认的前后端不一致

- `frontend/components/workbench-app.tsx` 的 `AI 平台入口` 导航项没有 `permission`，真实模式下所有登录用户都能看到。
- 后端 `GET /api/v1/engines` 要求 `engine.verify`（系统管理员持 `engine.manage` 也可）。
- 结果：`VIEWER`、`REVIEWER`、`LEAD_OPS` 点进去会 403 或空态；`SYS_ADMIN` 又可能因为不在项目里而拿不到 `engine.verify`，需要特判。

### 2.2 其他需要明确的页面

- `内部排障` 当前按 `monitoring.read` 展示，`VIEWER`、`REVIEWER` 也能看到失败码、trace 等内部诊断信息，偏宽。
- `线索管理` 导航没有权限字段，靠 `leadAccess` 在页面里显示“无权限”；`REVIEWER` 会看到一个自己不可用的菜单。
- `工作概览`、`项目管理`、`组件规范` 没有页面级权限。前两个是公共入口，问题不大；`组件规范` 是内部 UI 规范，不含业务敏感数据，可以保持登录可见。
- 当前导航只支持一个 `permission` 字符串，表达不了“满足 A 或 B 才可见”的场景。
- 当前 `snapshot.permissions` 是**当前项目**的角色能力；`engine.verify` 后端允许“任一项目持有”，前端会漏掉“在别的项目有该能力”的账号。

## 3. 分级模型

| 级别 | 判定 | 适用页面 |
|---|---|---|
| L0 公共 | 已登录即可 | 工作概览、项目管理、组件规范 |
| L1 项目只读 | 当前项目具备对应 read 能力 | 监测、题库、样本、内容、发布、渠道、报价、统计、指标、审核、FAQ、素材 |
| L2 项目操作 | 页面可见 + 对应 write/review/execute 能力 | 各页面的新增、编辑、审核、执行、导出按钮 |
| L3 项目管理 | 当前项目具备 `project.member.manage` / `audit.read` | 成员管理、操作日志 |
| L4 系统管理 | `isSystemAdmin` + `engine.manage` / `project.create` | AI 平台入口的编辑/测试、项目管理里的新建项目 |
| L5 全局委托 | 系统管理员，或任一项目具备 `engine.verify` | AI 平台入口的查看与网页端人工核验 |

## 5. 字段级可见性建议

### 5.1 AI 平台入口

| 角色 | 可见内容 |
|---|---|
| 系统管理员（`engine.manage`） | 平台、入口、URL、协议、模型、credential_ref、配置状态、测试连接 |
| 项目运营/项目管理员（`engine.verify`） | 平台名、入口名、入口类型、协议、模型、启停、最近核验；**不返回 API 入口 URL 和 credential_ref** |
| 无 `engine.verify` | 不显示页面 |

网页用户端/应用内搜索入口是人工核验对象，可对 `engine.verify` 展示其 URL；API 入口的 URL 与凭据变量名不对其展示。

### 5.2 内部排障

页面收紧到 `monitoring.execute` 或 `project.member.manage` 后，trace、失败码、请求摘要只对这些账号返回；`VIEWER`、`REVIEWER` 不再请求该接口。

### 5.3 线索

`lead.read` 才展示页面；`lead.write` 才展示新增/编辑。是否对 `lead.read` 但无 `lead.write` 的账号做手机号脱敏，作为单独业务决策，不混在本次页面分级里。

## 6. 实现方案

### 6.1 导航元数据

把当前 `permission?: string` 扩展为：

```ts
type NavScope = "public" | "project" | "global" | "system";

interface NavItem {
  id: Section;
  label: string;
  scope: NavScope;
  permissions?: string[];
  match?: "any" | "all";
  // system 页面使用 isSystemAdmin；global 页面使用 globalPermissions
}
```

`canSee` 改为：

```ts
function canSee(item, snapshot) {
  if (snapshot.source !== "live") return true;
  if (item.scope === "public") return true;
  if (item.scope === "system") return snapshot.isSystemAdmin === true;
  if (item.scope === "global") {
    return snapshot.isSystemAdmin === true ||
      hasAny(snapshot.globalPermissions, item.permissions);
  }
  return hasAnyOrAll(snapshot.permissions, item.permissions, item.match);
}
```

注意：不要把 `isSystemAdmin` 作为所有项目页面的兜底，否则系统管理员会看到自己无项目权限的业务页，点进去仍是 403。

### 6.2 全局能力

在 BFF 的 `frontend/app/internal/workbench/route.ts` 中，从 `me.projects` 汇总：

- `globalPermissions`：所有项目 `permissions` 的并集，至少包含 `engine.verify`。
- `isSystemAdmin` 继续单独传递。

这样“在 A 项目是运营、当前在 B 项目是只读”的账号，仍然能看到全局 AI 平台入口，和后端 `ensure_engine_verification_capability` 的“任一项目”口径一致。

### 6.3 后端配合

- `AI 平台入口`：后端已有 `engine.verify` / `engine.manage` 门禁，不需要改权限模型；只需要按角色裁剪 `EngineEntryData` 的敏感字段。
- `内部排障`：后端 `monitoring.py` 的诊断接口从 `monitoring.read` 收紧为“`monitoring.execute` 或 `project.member.manage`”。需要加一个 `require_any_permission` 依赖，或在服务层做等价校验。
- `线索`：后端已经是 `lead.read` / `lead.write`，前端导航补 `lead.read` 即可。
- 其他模块：后端门禁保持不变，前端只补导航元数据，避免出现“菜单可见但接口 403”。

### 6.4 测试

1. 前端 `canSee` 单元测试：6 个角色 × 全部导航项，断言可见/隐藏。
2. 后端权限测试：
   - `VIEWER` 访问 `/api/v1/engines` 返回 403；
   - `EDITOR` 可查看入口但看不到敏感字段；
   - `SYS_ADMIN` 可编辑/测试；
   - `VIEWER`/`REVIEWER` 访问诊断接口返回 403；
   - `LEAD_OPS` 可见线索，`REVIEWER` 不可见。
3. 前端 `tsc --noEmit`、后端定向 pytest。
4. 手工 E2E：分别用 6 个角色登录，检查菜单、页面、按钮、接口 403 是否一致。

## 7. 实施顺序

1. **P0**：`AI 平台入口` 导航补 `engine.verify`，系统管理员特判；补 `globalPermissions`。
2. **P1**：`内部排障` 收紧；`线索管理` 补 `lead.read`；统一 `scope/match` 元数据。
3. **P2**：AI 平台入口字段裁剪；诊断接口字段/路由收紧后的测试。
4. **P3**：按角色矩阵补 E2E；把矩阵写进 `docs/权限矩阵.md` 或现有权限文档，防止后续漂移。

## 8. 已确认的决策

以下四条已按建议实施：

1. `EDITOR` 只看 AI 平台入口的名称、类型、协议、模型、启停和最近核验；系统管理员看全量配置。
2. `VIEWER` / `REVIEWER` 不再看到“内部排障”；只保留 `EDITOR` 与 `PROJECT_ADMIN`。
3. `线索管理` 对无 `lead.read` 的账号直接隐藏；后端返回 `leadAccess=forbidden` 时也隐藏。
4. 系统管理员不直接管理项目成员；成员管理仍由 `project_admin` 负责。

`VIEWER` 线索联系方式脱敏已在首批实施；业务负责人“确认资料与优先级”和四类预算审批已在 2026-11-18 补齐，纳入同一套能力码分级，不再作为后续决策项。
