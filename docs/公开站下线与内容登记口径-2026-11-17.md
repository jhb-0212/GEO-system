# 公开站下线与内容登记口径（2026-11-17）

> 决策：**geo 不做公开站。对外公开页归公司官网 `https://www.gdccai.com`，两套部署各自独立。** geo 只负责“页面登记 + 事实口径 + 引用监测”。

## 1｜为什么下线

同一集团两个域名各挂一套公开页，会立刻出现三个问题：

1. 同一段课程文案出现在两个域名 → 重复内容，权重互相抵消；
2. 两份真源，公司站改一次、geo 侧不跟 → 页面文案开始漂移，谁改都怕漏；
3. geo 的公开页是静态构建产物，改一句话要重新发布，而公司站的发布节奏不归我们控。

结论：**geo 不承担对外呈现职责**，避免和公司官网形成内容竞争。原 7 页公开站（首页、基地介绍、两条课程页、公开事实页、FAQ、联系到访）与其 JSON-LD、sitemap、robots 一并撤除。

## 3｜页面登记口径：`public_pages` 从现在开始真正有用

表结构未改，用途变了：从“我们自己页面的登记”变成“**公司官网真实页面的登记**”。

- 一行 = 公司官网一个对外页面：`slug`（稳定标识）、`title`、`page_type`、`url`（公司站真实 URL）、`canonical_url`（一般指 `www.gdccai.com` 自身）、`publish_status`、`last_published_at`。
- 与 `content_plans.site_page_id` 关联：这条计划最终落在公司站哪个页面。
- 与引用归因关联：`citations` 里命中公司站 URL 的引用，才算“引用了我们自己的页面”，SOV 才准。
- 接口仍为 `GET / POST / PATCH /api/v1/projects/{project_id}/pages`，权限 `content.read` / `content.write`，无新增字段、无迁移。

## 4｜对外仍然可用的两条通道

1. **FAQ**：公司官网直接拉匿名只读端点 `GET /api/v1/public/projects/{project_code}/faqs`（不鉴权，只返 `published` 条目）。JSON-LD `FAQPage` 由公司官网页面生成。
2. **事实口径**：以公司官网当期页面为准；geo 侧只在内容写作与监测中对齐，不再维护第二份对外文案。

两个实现上的坑（已写进代码注释与单测）：

1. 官网当前 **`https` 证书主机名不匹配**，TLS 校验直接失败；脚本默认走 `http`，需要时用 `--base-url` 覆盖。
2. 资讯稿标题里常带“课程/培训班”字样，**不能按标题判课程页**——首轮把 8 条资讯误分成 `course`，改为只按路径判断（`/product/*` 才是课程），`--update` 已纠正。

## 7｜交付包导出（已实现）

公开页不归我们渲染，正文就不能靠人复述。新增只读接口：

`GET /api/v1/projects/{project_id}/content-versions/{version_id}/export`（权限 `content.read`）

返回一份可直接粘进公司站 CMS 的成品：

| 字段 | 内容 |
| --- | --- |
| `title` | 母稿标题 |
| `markdown` | `# 标题` + 正文；正文里的 `# 小标题` 自动降为 `## `，保证交付包只有一个 h1 |
| `html` | 纯文本正文转的基础 HTML（空行分段、`#`/`##`/`###` 降级为 h2/h3/h4、`- ` 转 `<ul>`），**尖括号已转义**，避免正文里的标签被当作 HTML 塞进编辑器 |
| `meta_description` | 正文压成一行、截 120 字，作为 SEO 摘要建议值 |
| `canonical_hint` | 若该母稿已登记过 `public_pages`，回填公司站真实 URL；没有则为 null |
| `jsonld` | `Article` 结构化片段（含 `mainEntityOfPage`/`url` 指向 canonical） |
| `checklist` | 5 条粘贴动作清单（标题、正文、摘要、canonical、发布后回填 `pages`） |
| `slug_suggestion` / `content_hash` | CMS slug 建议（**只取标题里的英文单词**；纯数字不参与，取不到就退回 `content-<item 前 8 位>`）；版本哈希用于"粘的是哪个版本" |

设计边界：**只出内容，不写库、不生成页面、不改 `public_pages`**。发布动作仍由人在公司站完成，完成后按既有 `PATCH /pages` 回填 URL 与 `publish_status`——这样发布是真动作，不是系统里写着"已发布"。

测试：`backend/tests/test_content_export_package.py` 2 项（HTML 转义 + 结构与清单；`public_pages` 关联时 canonical 与 JSON-LD 对齐）。全量 `pytest -q` **362 passed**。

联调中发现并修掉的两个小问题（都补了断言）：

1. 标题里只有数字时（如"交付包联调 2026-11-17"），slug 会被拼成 `2026-11-17`；改为只取英文单词，纯数字不参与。
2. 摘要原样带出 `# `、`- ` 标记和正文里的标签；改为先剥掉行首标记与 HTML 标签再截断。

另外本轮跑审计脚本时它报出 `映射缺失：brand_profiles`——另一个并行开发分支新加了品牌口径表。已补 `TABLE_RESOURCE` / `RESOURCE_SECTION` 映射（`brand_profiles → brand-profile → brand`），现在矩阵是 **43 张表（完整 32、豁免 3、缺口 0）**，`--strict` 退出码 0；`--self-test` 3/3 仍 PASS。

## 8｜引用归因：品牌口径与自有域名（已就位，本轮做核对与数据修正）

结论：**这套配置由并行开发分支先落地了，本轮不重复造，做的是核对链路 + 修一处会污染指标的数据。**

### 8.1｜配置在哪、是什么

`brand_profiles`（一项目一行，`is_active` 控制生效），由 `backend/scripts/setup_brand_profile.py` 建立。`gz-base` 当前实际值（接口 `GET /api/v1/projects/{id}/brand-profile` 读出）：

| 字段 | 值 | 驱动什么 |
| --- | --- | --- |
| `canonical_name` | 广东省AI数字人才就业实训基地 | `brand_mentioned` |
| `aliases` | 同名 + 广东省成才人工智能产业孵化有限公司 + 成才 | `brand_mentioned` |
| `identifiers` | 番山创业中心1号楼2区207 / 番山创业中心1号楼2区2楼 / 番禺大道北537号 / 19927547288 | `brand_identified`（没点名但有唯一标识） |
| `owned_domains` | `gdccai.com`（`clean_domains` 会去掉 `www.` 并小写） | `citations.is_brand_related` → `stats.citation_share` |
| 权限 | 读 `monitoring.read`，写 `brand.manage`（editor + project_admin） | — |

三类词条刻意分开，不合并：点名才算提及；有标识但没点名单独统计；自有域名只影响信源占比，不参与 `brand_identified`。

### 8.2｜链路

`services/brand_profile.py::build_vocabulary` → `clean_domains(owned_domains)` → 采集时 `monitoring_collection.py:683/812` 传 `brand_domains` → `monitoring_extraction.py:269` 建 `brand_domain_set`、`:323-326` 命中即写 `is_brand_related=True` → `stats.py:737/741` 统计 `brand_citations`、`:876` 出 `citation_share = brand_citations / citation_total`。

有测试：`backend/tests/test_brand_profile.py:258-289`（命中写 True；未配置自有域名时保持 False）。

### 8.3｜修掉一处污染：边界样本把"未知域名"标成了自有

`monitoring_citations` 39 条里唯一两条 `is_brand_related=true` 的域名是 `unknown-1.edge.example` / `unknown-2.edge.example` —— 边界样本的"未知域名待归类"数据。溯源到 `backend/scripts/seed_validation_samples.py::get_or_create_citation` 硬写 `is_brand_related=True`，域名根本不在 `owned_domains` 里。后果：`citation_share` 会显示 2/39 ≈ 5.1%，把"我们掌控了自己的信源"这件没发生的事写成发生了。

已改为 `False`（加注释说明为什么不能标 True），并把库里这两行 `UPDATE` 回 `False`。复核：`is_brand_related` 计 0。

修正后 `GET /stats/overview`（gz-base）：`valid_answers=6`、`brand_mentioned_answers=0`、`brand_identified_answers=1`、`brand_mention_rate=0.0`、`brand_identified_rate=0.1667`、`citation_rate=0.0`。也就是说当前 dev 库里没有任何一条引用来自公司站——这是真实状态，不是配置漏了。
