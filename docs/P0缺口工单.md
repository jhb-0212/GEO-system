## 3. 批量生成响应契约

### 3.1 字段定义

| 字段 | 定义 |
| --- | --- |
| `round_id` | 本次生成所属轮次 UUID |
| `requested_question_count` | 本项目题目总数（含 `draft`/`active`/`archived`） |
| `eligible_question_count` | 可参与生成的题目数：`status=active` 且 `current_version_no` 有对应 `question_versions` |
| `inactive_question_count` | `status` 为 `draft`/`archived` 的题目数 |
| `inactive_question_ids` | 未激活题目 UUID，**按 `code` 升序** |
| `inactive_questions` | `id/code/title/status` 明细，按 `code` 升序 |
| `question_version_missing_count` | `active` 但当前版本不存在的题目数 |
| `question_version_missing_question_ids` | 上述题目 UUID，按 `code` 升序 |
| `engine_count` | 当前项目内“启用引擎 + 至少一个启用入口”的去重引擎数；每个引擎只取一个有效入口 |
| `expected_task_count` | `requested_question_count × engine_count`，理论基线值 |
| `eligible_expected_task_count` | `eligible_question_count × engine_count`，实际可生成上限 |
| `created_task_count` | 本次真正新建的任务数 |
| `reused_task_count` | 幂等命中、复用既有任务的数量 |
| `generated_task_count` | **`created_task_count + reused_task_count`**，本次响应覆盖的任务数 |
| `complete` | 是否形成完整基线，判定见 3.4 |
| `skipped_reason` | `null` / `inactive_questions` / `engine_entries_insufficient` / `question_version_missing` |

### 3.4 `complete` 判定与 `skipped_reason` 优先级

```text
complete = (
    generated_task_count == expected_task_count
    AND eligible_question_count == requested_question_count
    AND engine_count == 4
    AND question_version_missing_count == 0
    AND skipped_reason IS NULL
)
```

- 成功：`generated=expected`、`eligible=requested`、`engine_count=4`、无缺版本、`skipped_reason=null`
- 全量未激活：`generated=0`、`complete=false`、`skipped_reason="inactive_questions"`
- 部分未激活：`generated=16/24`、`complete=false`、`skipped_reason="inactive_questions"`
- 引擎不足 4 个：`engine_count<4`、`expected=requested×实际引擎数`、`complete=false`、`skipped_reason="engine_entries_insufficient"`
- active 但当前版本缺失：`generated=0`、`complete=false`、`skipped_reason="question_version_missing"`

`skipped_reason` 只返回一个主因，优先级：

1. `question_version_missing`（数据完整性阻断）
2. `engine_entries_insufficient`（无法形成 24 格）
3. `inactive_questions`（部分或全部未激活）
4. `null`

## 4. 硬约束

1. **不能静默少生成**：`generated_task_count < expected_task_count` 时 `complete=false`，并返回未生成原因；不得只返回一个 0 条任务的空列表。
2. **不能生成 draft 任务**：正式任务只引用 `active` 且当前版本存在的题目；active 但当前版本缺失时整批阻断，`skipped_reason="question_version_missing"`。
3. **幂等**：幂等键为 `round_id + question_version_id + engine_entry_id + sampling_no`，与现有唯一约束 `uq_monitoring_tasks_round_question_entry_sampling` 一致；基线每格 `sampling_no=1`，请求体不传采样序号，本期不支持同轮次多次采样。
4. **幂等计数**：首次 `created=24, reused=0, generated=24`；重放 `created=0, reused=24, generated=24, complete=true`。`generated` 不是“本次新建”，而是“本次覆盖（新建+复用）”。
5. **并发幂等**：同一轮次并发两次批量请求，第二次必须全部 `reused`；实现用轮次行锁或 `INSERT ... ON CONFLICT DO NOTHING` + `RETURNING` 判定 created/reused。现有唯一约束已含 `round_id`，`project_id` 由轮次归属保证，本期不新增冗余迁移。
6. **引擎范围**：只取当前项目内 `is_active=true` 的引擎，且每个引擎至少一个 `is_active=true` 的入口；每个引擎只选一个有效入口，按 `ai_engines.code`、入口 `created_at`、`id` 稳定排序。`engine_count<4` 时 `complete=false`、`skipped_reason="engine_entries_insufficient"`；`engine_count=0` 时不生成任务。
7. **本期用 200 表达业务不完整**：全量/部分未激活、引擎不足、版本缺失统一返回 `200 + complete=false + skipped_reason`。`409 inactive_questions` 只作为错误信封扩展后的目标态，不进入本期验收；前端按 200 解析。
8. **测试流程隔离**：未来草稿预览走独立 `dry_run` 或独立端点，不写正式任务表。

### 4.2 B1 认证范围裁决（C 复核 2026-11-13；最终口径已更新）

> **最终决定（2026-11-13，覆盖下方原裁决，以 PR #24 实现为准）**：经重新评估，本期 P0-B1 在 `POST /auth/login`、`GET /auth/me` 之外，**同时交付修改密码与 `token_version` 机制**。原因：登录凭证有效期 8 小时，改密或账号异常时必须让已签发的旧凭证立即失效，否则旧凭证在过期前仍可使用。实现方式为 `users.token_version` 版本号比对（改密即 +1，旧 JWT 当场作废），不引入 Redis 黑名单或 sessions 表。下方原“不做改密、不引入 token_version”的裁决作废，仅保留决策过程记录。

裁决（已被上方最终决定覆盖，留档）：本期 `P0-B1` 只交付 `POST /auth/login`、`GET /auth/me`；**不做改密、不引入 `token_version`，因此没有 `token_stale`**。之前关于 `token_version` 的评审清单作废，不再要求迁移加列、JWT 加 `tv`、改密后失效。

代码现状（PR #24，已合入 main）：

1. 登录成功回写 `last_login_at`（UTC），失败不回写；
2. 用户名不存在与密码错误统一返回 401 `unauthorized`，不暴露账号是否存在；
3. `me.projects` 只返回当前用户仍是活跃成员的项目；系统管理员不因 `is_system_admin` 自动拿全量；
4. 停用账号 401 `user_inactive`；改密递增 `token_version`，旧 JWT 带旧 `tv` 返回 401 `token_stale`；
5. 测试覆盖：登录成功/密码错/用户不存在、`last_login_at` 写入与失败不写、`me` 无 token、停用账号、普通成员项目、系统管理员无成员/有成员、改密后旧 token 失效。

> （已被本节最终决定覆盖，留档）原表述：改密与令牌硬失效留到后续版本，不纳入本次 P0-B1 验收；不新增 `sessions` 表、Redis 黑名单或 `password_changed_at`。实际最终方案仅新增 `token_version` 一列，仍不引入 sessions 表或 Redis 黑名单。
