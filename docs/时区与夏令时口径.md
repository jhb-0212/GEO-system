适用范围：`backend/app/services/time_windows.py`、`workbench_todos.py`、`api/workbench.py`、前端工作台待办中心
最后更新：2026-11-26

## 1. 为什么需要这份口径

「库里存的是 UTC」不等于「业务自然日窗口算对了」。两件事必须分开验证：

- 存储层：`timestamptz` 是否写入了正确的瞬时（UTC）。
- 解释层：这个瞬时属于项目所在时区的哪一天，`[start, end)` 边界落在哪个 UTC 时刻。

历史上出现过两类偏差：用浏览器本地时区推自然日（前端）；用固定 `86_400_000 ms` 当一天（DST 日实际 23h/25h）。本文件把规则固定下来，代码与测试都以此为唯一口径。

## 2. 规则

1. **时区唯一来源是 `Project.timezone`**（IANA 名称）。不接受调用方传偏移量；`tz_offset_minutes` 已废弃，仅写遥测，不参与窗口计算。
2. **存储与查询统一 UTC**：`timestamptz` 列、`entered_todo_at`、`generated_at` 全部是瞬时；展示时才转项目时区。
3. **自然日窗口 = 本地 00:00 到次日 00:00，左闭右开** `[start, end)`。周窗口 = 本周一 00:00 到下周同一 00:00（周一为周起点，`weekday()` 语义）。
4. **DST 结束（本地时间重复，ambiguous）**：取 `fold=0`，即第一次出现的那个瞬时（较早的 UTC）。理由是可预期、可复现，且与"当天从 00:00 开始算"一致；同一本地墙钟时间不会因为 fold 选择而在两个窗口里各算一次。
5. **DST 开始（本地时间不存在，nonexistent）**：本地 00:00 通常不受影响；个别时区在 00:00 前后跳变时，取当日第一个真实存在的瞬间，并校验「UTC 转回该时区后日期不得漂移」，漂移则报 `ProjectTimezoneInvalid`，不做隐式平移。
6. **禁止固定毫秒数当日长**：禁止 `86_400_000` / `86400000` / `getTimezoneOffset()` 参与业务窗口；DST 日的 23h/25h 由 tzdata 决定。
7. **前端只消费服务端窗口**：`business_timezone`、`window.start`、`window.end`、`generated_at` 由后端返回，前端不得自行推导自然日；待办计数按服务端窗口过滤。
8. **非法时区显式失败**：空串视为脏数据直接报错（`project_timezone_invalid`），不静默回退默认时区。

## 3. 已验证的边界（硬编码期望，不由被测函数生成）

| 场景 | 期望（UTC） |
| --- | --- |
| Asia/Shanghai 2026-11-26 | 2026-11-25T16:00Z → 2026-11-26T16:00Z（24h） |
| UTC 2026-11-26 | 2026-11-26T00:00Z → 2026-11-27T00:00Z |
| America/New_York 2026-03-08（DST 开始） | 2026-03-08T05:00Z → 2026-03-09T04:00Z（23h） |
| America/New_York 2026-11-01（DST 结束） | 2026-11-01T04:00Z → 2026-11-02T05:00Z（25h） |
| Europe/Berlin 2026-03-29（DST 开始） | 2026-03-29T23:00Z → 2026-03-30T22:00Z（23h） |
| Europe/Berlin 2026-10-25（DST 结束） | 2026-10-25T22:00Z → 2026-10-26T23:00Z（25h） |
| Asia/Tokyo（无 DST） | 固定 UTC+9，窗口恒 24h |

### 午夜本身重复或不存在（补充证据）

普通 DST 场景是"白天跳变"，不覆盖本地 00:00 自身异常。以下三例来自 tzdata 实测：

| 场景 | 时区 / 本地日 | 实测事实 | 期望行为 |
| --- | --- | --- | --- |
| 午夜重复 | `Atlantic/Azores` 2026-10-25 | 01:00 回拨到 00:00，00:00 出现两次（00:00Z 与 01:00Z） | 取 `fold=0`，日界 `2026-10-25T00:00Z`；该日 25 小时 |
| 午夜不存在 | `America/Sao_Paulo` 2018-11-04 | 00:00 直接跳到 01:00 | 取当日首个真实瞬间 `03:00Z`（本地 01:00），不报错、不返回前一日 |
| 整日被跳过 | `Pacific/Apia` 2011-12-30 | 跨日期线跳日，往返后日期漂移 | 抛 `ProjectTimezoneInvalid` |

反例说明：`America/Havana 2026-11-01` 的午夜并不重复（古巴在 01:00 回拨，00:00 只出现一次），不能作为 `fold=0` 的测试样本；`Atlantic/Azores 2026-10-25` 才是有效样本。

## 5. 已知限制（不作为通过依据）

1. 期望值依赖 tzdata 版本。CI 与本地都用系统 tzdata；跨大版本升级时需重跑矩阵并更新本表，不视为回归。
2. 1937 年前的中国历史时区（地方平时）不纳入业务范围。
3. mock 前端的窗口是固定样本（上海 11-26），前端不变性用例只证明"浏览器时区不参与计算"，不替代服务端真实库矩阵。
4. 生产环境的权限补齐与迁移演练不在本口径范围，属于部署窗口事项。
