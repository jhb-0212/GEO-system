# 定时探活与告警

## 为什么需要

服务"活着"不等于"可用"：进程在跑、但数据库连不上、公开接口被限流打挂、迁移没跑完，这些都不会让容器退出。
仓库里原本只有：

- 业务任务失败告警（`task_alert_webhook`，由 worker 在任务失败时推送）；
- 手工执行的 `backend/scripts/worker_healthcheck.py`（检查 worker 心跳）。

没有"每隔几分钟自动确认一次服务可用"的机制。本文件补齐这一层：探活脚本 + 定时调度 + 告警。

## 探活脚本

`deploy/scripts/probe_health.sh`，检查三项：

| 检查 | 失败含义 |
|---|---|
| `GET /health` 200 且 `status=ok` | API 进程不可用或未启动完成 |
| `GET /health/db` 200 | 数据库连不上（迁移失败、连接池耗尽、PG 挂了） |
| `GET /api/v1/public/projects/{code}/faqs` 200 | 公开只读链路异常（Redis 故障也会在这里暴露，因为限流依赖 Redis） |

环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `GEO_BASE_URL` | `http://127.0.0.1:8080` | 探活基址；生产填对外域名或本机 nginx 端口 |
| `GEO_PROBE_PROJECT_CODE` | `gz-base` | 公开 FAQ 检查用的项目 code |
| `GEO_ALERT_WEBHOOK` | 空 | 群机器人地址（飞书/钉钉 text 格式）；留空只打日志 |
| `GEO_PROBE_TIMEOUT` | `10` | 单次请求超时秒数 |

退出码：全部通过为 0，任一失败为 1（便于调度器判定）。

## 接入方式（三选一）

### 1. Linux cron（最简单）

```cron
# 每 5 分钟探活一次，失败时脚本自己推 webhook
*/5 * * * * GEO_BASE_URL=http://127.0.0.1:8080 GEO_ALERT_WEBHOOK=https://open.feishu.cn/open-apis/bot/v2/hook/xxx bash /opt/geo/deploy/scripts/probe_health.sh >> /var/log/geo-probe.log 2>&1
```

### 2. systemd timer（推荐，带日志与失败可见性）

`/etc/systemd/system/geo-probe.service`：

```ini
[Unit]
Description=GEO health probe
After=network.target

[Service]
Type=oneshot
Environment=GEO_BASE_URL=http://127.0.0.1:8080
Environment=GEO_ALERT_WEBHOOK=https://open.feishu.cn/open-apis/bot/v2/hook/xxx
ExecStart=/bin/bash /opt/geo/deploy/scripts/probe_health.sh
```

`/etc/systemd/system/geo-probe.timer`：

```ini
[Unit]
Description=Run GEO health probe every 5 minutes

[Timer]
OnBootSec=2min
OnUnitActiveSec=5min
Unit=geo-probe.service

[Install]
WantedBy=timers.target
```

启用：`systemctl enable --now geo-probe.timer`，查看：`systemctl list-timers geo-probe.timer`。

### 3. Windows 计划任务（本机或内网部署）

脚本是 bash，Windows 上通过 Git Bash 调用：

```powershell
$action = New-ScheduledTaskAction -Execute "C:\Program Files\Git\bin\bash.exe" `
  -Argument "-lc 'GEO_BASE_URL=http://127.0.0.1:8080 GEO_ALERT_WEBHOOK=<webhook> bash /c/geo/deploy/scripts/probe_health.sh'"
$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date).AddMinutes(2) `
  -RepetitionInterval (New-TimeSpan -Minutes 5)
Register-ScheduledTask -TaskName "GEO 探活" -Action $action -Trigger $trigger -RunLevel Highest
```

## 告警与处置

- 告警文案固定以 `[GEO 探活失败]` 开头，便于在群里做关键词过滤。
- 收到告警先手工跑一次脚本，确认是持续性故障还是瞬时抖动。
- `/health/db` 连续失败：先看 `docker compose logs api postgres`，再确认迁移是否跑完（`alembic current`）。
- 公开 FAQ 接口 429：说明当前 IP 触发限流（默认 30 次/分钟），先确认不是探活频率过高。
- **日志出现 `ip limiter unavailable; allow request`**：限流组件已降级放行（Redis 不可用时的既定取舍），此时公开接口处于无保护状态。处置：先恢复 Redis，再确认 `REDIS_URL` 与密码；期间如发现异常流量，临时把 `PUBLIC_FAQ_PER_MINUTE` 之外的手段（网关限速 / 临时下线该接口）顶上。

## 脚本调用约定

- 所有调度一律用 `bash <脚本路径>` 调用，不依赖可执行位：脚本在 Windows 上创建、提交时 Git 可能记录为 `100644`，直接执行会在 Linux 上 `Permission denied`，而失败方式是"静默不告警"。
- 如需直接执行，用 `git update-index --chmod=+x deploy/scripts/probe_health.sh` 后重新提交，并在部署机上确认 `ls -l` 显示 `-rwx`。

## 与 `task_alert_webhook` 的关系

两者可以指向同一个群机器人，但语义不同：

- `task_alert_webhook`：业务任务失败（某次监测任务超时、发布核实失败）；
- `GEO_ALERT_WEBHOOK`：服务不可用（进程、数据库、公开链路）。

不建议合并成一个开关：运维告警不应因为业务告警被关闭而一起消失。
