# 发布版本治理（CI-first，含可选分支保护）

> 本文件定义 `CURRENT_MAIN`、`RELEASE_TAG`、`RELEASE_COMMIT`、`IMAGE_DIGEST`、`DEPLOYED_COMMIT` 的操作口径，不保存会变化的 commit 或测试数量。

## 一、版本变量

| 变量 | 唯一来源 | 操作命令 | 禁止用法 |
| --- | --- | --- | --- |
| `CURRENT_MAIN` | `origin/main` | `git fetch origin && git rev-parse origin/main` | 不用它直接构建生产 |
| `RELEASE_TAG` | 正式 annotated tag | `git for-each-ref refs/tags/<tag>`；必须是 `tag` 对象 | 不用 lightweight tag、`archive/*` 或分支名冒充 |
| `RELEASE_COMMIT` | tag peeled commit | `git rev-list -n1 refs/tags/<tag>` | 不用浮动分支 HEAD 或历史 commit 冒充 |
| `IMAGE_DIGEST` | GitHub Release manifest 的 `repo_digest` | `jq -r '.images.backend.repo_digest' release-manifest.json` | 不用本地 Image ID、镜像 tag 或 label 代替 |
| `DEPLOYED_COMMIT` | 运行容器 OCI revision label | `deploy/scripts/verify_release.py` | 不用 manifest/CI 日志代替实际检查 |

## 二、发布流程（唯一入口）

1. PR 合入 `main` 前，`backend-ci` 的 `backend-test`、`frontend-check`、`frontend-e2e-mock` 三个检查必须全绿；不能只用本地 `pytest` 结果代替。
2. 在合入后的固定 commit 上创建 annotated tag（`v<版本>`），推送 tag：
   ```bash
   git tag -a v1.0.0 -m "GEO System v1.0.0" <main-commit>
   git push origin v1.0.0
   ```
3. tag push 自动触发 `.github/workflows/release.yml`。workflow 必须完成：
   - annotated tag object、peeled commit、远端 tag object 一致；
   - **tag peeled commit 必须等于触发本次 workflow 的 `github.sha`**；不一致说明 tag 在触发后被移动，立即失败，不得进入 Buildx 或 GHCR 推送；
   - tag commit 可达 `origin/main`；
   - checkout 的 `HEAD == tag commit`，工作区干净；
   - GitHub Release 是否已存在必须由 API 明确判定：HTTP 200 已存在则拒绝；HTTP 404 确认不存在才继续；401/403/429/5xx、网络错误或无法解析响应一律失败关闭；不得用 `gh release view` 的“非 0 退出”代替“不存在”；
   - exact-SHA 的 `backend-ci` Push run 三个 job 全绿；
   - 从 tag checkout 构建并推送 backend/frontend 到 GHCR，采集 `repo_digest`；
   - 生成 manifest，作为 workflow artifact 与 GitHub Release asset 附加。
4. 部署主机登录 GHCR（只读即可）：
   ```bash
   docker login ghcr.io
   ```
   从 GitHub Release 下载 `release-manifest.json`，把其中 digest-pinned 引用写入 `deploy/.env.prod`：
   ```bash
   BACKEND_IMAGE=ghcr.io/<owner>/geo-backend@sha256:<digest>
   FRONTEND_IMAGE=ghcr.io/<owner>/geo-frontend@sha256:<digest>
   ```
5. 只拉取镜像启动，禁止本地 build：
   ```bash
   docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.prod up -d --no-build
   ```
6. 部署完成后运行：
   ```bash
   python deploy/scripts/verify_release.py --manifest deploy/releases/v1.0.0.json
   ```
   所有 `migrate` / `api` / `worker` / `beat` / `frontend` 容器的 revision label 必须等于 manifest.commit，
   `RepoDigests` 必须包含完整的 `repo@sha256:<digest>` 引用，不能把“仓库名匹配”和“digest 匹配”分散到两个不同条目分别满足；
   空 label、`unknown`、仓库或 digest 不一致一律失败。
   `migrate` 一次性容器还必须 `State.Status == exited` 且 `State.ExitCode == 0`；缺少 State、未退出或退出码非 0 一律失败。
7. 把命令输出写进当次生产部署记录；没有实际输出不能勾选“版本锚定”。

## 四、Tag 不可变治理

- 正式 release tag 一旦发布不允许移动、删除或重打；修复版本新建 tag。
- 同一 tag 的 GitHub Release 已存在时，release workflow 必须在 Buildx 构建和 GHCR 推送前失败；Release 查询只有 HTTP 404 才表示“不存在”，200 表示已存在，其它 HTTP/网络错误失败关闭；不得通过重跑旧 tag 改写镜像标签或覆盖既有 manifest asset。
- 每次 Release/部署重新核对远端 tag object 与 commit；远端 tag 与历史 manifest 不一致时拒绝部署，并报告“版本引用被改写”。
- **Tag 不可移动的实际保护（2026-11-23 已启用）**：仓库已改为 public，GitHub Rulesets 对 public 仓库强制执行。当前规则 `Release tag immutability`（ruleset id `27886264`，API：`GET /repos/jhb-0212/GEO-system/rulesets/27886264`）为 `active`，目标 `refs/tags/v*`，规则为 `update`、`deletion`、`non_fast_forward`；不限制创建，release workflow 仍可新建 `v*` tag。Bypass list 为空。`github.sha == tag peeled commit` 检查继续保留，作为发现 tag 移动/事件不一致的第二道检查。该规则不保护非 `v*` tag；且当前尚无 `v*` tag，页面显示 `Applies to 0 targets`，因此“配置已启用”不等于“已用真实 tag 证明拒绝更新/删除”。首个正式 Release 前必须补一次真实 tag 的拒绝更新/删除证据，或明确记录该演练缺口。
- 该治理不要求启用 `main` 分支保护。

## 五、`main` 分支保护（当前决定：不启用）

2026-11-23 项目 owner 明确：阶段 A 不要求配置 `main` 分支保护，该项不作为验收阻塞。CI 仍在每个 PR 上执行，合并前以 PR 的 `backend-test` / `frontend-check` / `frontend-e2e-mock` 结果为准。

若后续改为强制门禁，再按以下建议项配置并留证；仓库内不保存管理员令牌。

| 项 | 建议 |
| --- | --- |
| Require a pull request before merging | 开启；禁止直接 push `main` |
| Required status checks | `backend-ci / backend-test`、`backend-ci / frontend-check`、`backend-ci / frontend-e2e-mock` |
| Require branches to be up to date | 开启 |
| Require conversation resolution | 开启 |
| Do not allow bypassing | 对管理员同样生效（Include administrators） |
| Allow force pushes / deletions | 关闭 |

> 背景：仓库已于 2026-11-23 改为 public，classic branch protection 已具备启用条件；项目 owner 仍决定当前阶段不启用 `main` 分支保护，该项不作为阶段 A 的验收阻塞。若未来启用，按上表口径配置。

## 六、证据保存

- release manifest：GitHub Release asset 与 Actions artifact；本地核验时复制为 `deploy/releases/<tag>.json`，不提交主分支。
- 部署版本核验输出：`verify_release.py` 原始 stdout。
- CI 结果：以对应 commit 的 `backend-ci` run URL 为准。
- 镜像身份：manifest 的 `repo_digest` 与 `docker buildx imagetools inspect` 输出；`image_id` 不作为跨主机证据。
- 分支保护截图/API JSON：仅在后续启用强制门禁时留存；当前不启用，不作为交付项。
