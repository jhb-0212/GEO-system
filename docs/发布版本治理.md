# 发布版本治理（含可选分支保护）

> 本文件定义 `CURRENT_MAIN`、`RELEASE_COMMIT`、`DEPLOYED_COMMIT` 的操作口径，不保存会变化的 commit 或测试数量。

## 一、三个版本变量

| 变量 | 唯一来源 | 操作命令 | 禁止用法 |
| --- | --- | --- | --- |
| `CURRENT_MAIN` | `origin/main` | `git fetch origin && git rev-parse origin/main` | 不用它直接构建生产 |
| `RELEASE_COMMIT` | 正式 release tag | `git rev-list -n1 refs/tags/<tag>` | 不用浮动分支 HEAD 或历史 commit 冒充 |
| `DEPLOYED_COMMIT` | 运行容器 OCI label | `deploy/scripts/verify_release.py` | 不用 manifest/CI 日志代替实际检查 |

## 二、发布流程

1. PR 合入 `main` 前，`backend-ci` 的 `backend-test`、`frontend-check`、`frontend-e2e-mock` 三个检查必须全绿；不能只用本地 `pytest` 结果代替。
2. 在合入后的固定 commit 上创建 annotated tag（建议 `v<版本>`），推送 tag。
3. 在 tag 上运行：
   ```bash
   python deploy/scripts/create_release_manifest.py --tag <tag>
   ```
   产物写入 `deploy/releases/<tag>.json`，作为 GitHub Release asset 附加；不提交 `main`。
4. 部署时从 `deploy/.env.prod` 注入 `RELEASE_COMMIT`（值取自 tag），compose 会把它作为构建参数写入镜像的 `org.opencontainers.image.revision` label。
5. 部署完成后运行：
   ```bash
   python deploy/scripts/verify_release.py --manifest deploy/releases/<tag>.json
   ```
   所有 `api` / `worker` / `beat` / `frontend` 容器 label 必须等于 `RELEASE_COMMIT`；未设置 `RELEASE_COMMIT` 或 label 为 `unknown` 一律失败。
6. 把命令输出写进当次生产部署记录；没有实际输出不能勾选“版本锚定”。

## 三、当前状态与阻塞

- 截至 2026-11-23，仓库只有 `archive/*` 归档标签，**尚无正式 release tag**，因此 `RELEASE_COMMIT` / `DEPLOYED_COMMIT` 为空；这是阶段 A 之后发布流程的起点，不是当前运行值。
- `RELEASE_COMMIT` 未设置时，生产 compose 会在变量解析阶段失败，避免误用浮动分支构建。

## 四、`main` 分支保护（当前决定：不启用）

2026-11-23 项目 owner 明确：阶段 A 不要求配置 `main` 分支保护，该项不作为验收阻塞。CI 仍在每个 PR 上执行，合并前以 PR 的 `backend-test` / `frontend-check` / `frontend-e2e-mock` 结果为准。

若后续改为强制门禁，再按以下建议项配置并留证；仓库内不保存管理员令牌。

| 项 | 建议 |
| --- | --- |
| Require a pull request before merging | 开启；禁止直接 push `main` |
| Required status checks | `backend-ci / backend-test`、`backend-ci / frontend-check`、`backend-ci / frontend-e2e-mock` |
| Require branches to be up to date | 开启 |
| Require conversation resolution | 开启 |
| Do not allow bypassing | 对管理员同样生效（Include administrators） |
| Allow force pushes / deletions | 关闭 |

> 背景：当前仓库是个人账号下的私有仓库，GitHub 提示 classic branch protection 在迁到 GitHub Team/Enterprise 前不会强制执行。既然项目当前不要求强制门禁，就不再把它列为阶段 A 的未完成项；未来若启用，需先升级计划或改为公开仓库。

## 五、证据保存

- release manifest：`deploy/releases/<tag>.json`（GitHub Release asset，勿提交主分支）
- 分支保护截图/API JSON：仅在后续启用强制门禁时留存；当前不启用，不作为交付项
- 部署版本核验输出：`verify_release.py` 原始 stdout
- CI 结果：以对应 commit 的 `backend-ci` run URL 为准
