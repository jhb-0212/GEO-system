# B 交接说明：24 格基线采集与复核（2026-11-17）

> 这份是给 B 的操作单。目标只有一个：**把 6 题 × 4 引擎 = 24 格基线跑满，并留下可复核的记录。**
> 计划第 1 周的验收条件就是这一条：「24 个测试格均有有效结果或明确失败原因」。

## 一、三条硬约束（踩了会返工）

1. **基线轮次全项目只能有一个**。`monitoring_rounds` 上 `is_baseline=true` 是唯一索引，建第二个会直接报错。目前 `gz-base` 还没有基线轮，可以建。
2. **任务唯一键 = 轮次 + 题目版本 + 引擎入口 + 采样序号**。同一轮里重跑同一格要加 `sampling_no`；跨轮复测要新建轮次。否则会互相覆盖，历史记录就废了。
3. **每题必须新开对话，并记录联网模式**。`sampling_mode` 只有 `search_on` / `search_off` 两个值，本轮统一 `search_on`——同一格里混用两种模式，数据不可比。

## 二、执行步骤

**1) 建基线轮次**

```
POST /api/v1/projects/{project_id}/monitoring/rounds
{ "name": "首月基线 2026-11", "is_baseline": true }
```

`seq` 由后端自增，不用手填。

**2) 批量生成 24 个任务**

```
POST /api/v1/projects/{project_id}/monitoring/rounds/{round_id}/tasks/batch
```

生成规则是「本轮全部 active 题目 × 全部 active 引擎入口 × 采样序号 1」。所以**先确认两件事**再点：

- `questions` 里 6 题都是 `active`（Q01–Q06，`current_version_no=2`）→ 现在确实是 6 条；
- `ai_engine_entries` 里 `is_active=true` 的入口数——**这个数在变，别照抄本文档的数字**，先自己查一遍：

```powershell
cd backend
$env:PYTHONPATH = "C:\Users\EDY\Desktop\GEO系统开发\geo-system\backend"
.\.venv\Scripts\python.exe -c "import sys; sys.path.insert(0,'.'); from sqlalchemy import create_engine,text; from app.core.config import settings; e=create_engine(settings.database_url); print(e.connect().execute(text(\"select en.name,e.name,e.entry_type from ai_engine_entries e join ai_engines en on en.id=e.engine_id where e.is_active order by e.entry_type\")).all())"
```

**2026-11-17 16:00 实测：7 个 active 入口，直接批量生成会出 6 × 7 = 42 个任务，不是 24 个。**

| 引擎 | 入口 | 类型 | 支持联网 | 本轮是否该纳入 |
| --- | --- | --- | --- | --- |
| DeepSeek | 联网搜索（Responses 工具） | api | ✅ | 单列（生成式回答口径） |
| 豆包 | 搜索（方舟 Responses） | api | ✅ | 单列（生成式回答口径） |
| 百度文心 | 文心搜索（千帆 AI 搜索） | api | ✅ | 单列 |
| 百度文心 | 千帆 API | api | ❌ `supports_search=false` | **排除** |
| 豆包 | 网页端 | web_user | ✅ | 计划内 |
| 腾讯元宝 | 网页端 | web_user | ✅ | 计划内 |
| 百度文心 | 网页端 | web_user | ✅ | 计划内 |

计划要的是「6 题 × 4 个国内 AI 产品」的**用户端**基线，所以本轮应只留 4 个网页端入口（DeepSeek 网页端当前是废弃状态，需确认用 API 入口替代时如何标注），其余改 `is_active=false`，跑完再恢复。

**两个不能混的点**：

1. **API 入口返回的是生成式回答（`answer_kind=answer`），网页端采集的是用户看到的对话页**。两者回答风格、引用展示都不同，混在同一轮里会稀释指标，必须分组呈现。
2. **豆包网页端入口 `entry_url` 为空、备注写"待运营核验后填写"**，说明它靠网页桥而不是 API；能不能跑取决于桥是否接上豆包，先试一格再批量。

**3) 逐格执行**

```
POST /api/v1/projects/{project_id}/monitoring/tasks/{task_id}/execute
```

每格独立执行、独立留痕。失败不要重试到成功为止——失败本身是有价值的数据。

**4) 失败的记法**

失败写 `failure_code`，枚举是固定的：`login_blocked` / `timeout` / `access_blocked` / `captcha` / `rate_limited` / `other`。

**失败样本不进分母**（`stats.py` 只把 `hit` / `miss` 计入 `valid_answers`），所以"24 格里有 5 格失败"和"24 格里有 5 格没跑"是完全不同的两件事：前者验收通过，后者不通过。

**5) 人工复核（可选但强烈建议）**

如果某格答案明显被截断、或品牌判断拿不准，走 `POST /monitoring/samples/{sample_id}/review` 标成 `hit`/`miss`，不要直接改样本状态。

## 三、跑完交回什么

| 项 | 说明 |
| --- | --- |
| 轮次 `seq` 与 `round_id` | 后续复核脚本要按轮次筛 |
| 24 格结果分布 | 有效（hit+miss）多少、失败多少、失败原因各几条 |
| 引用条数 | 本轮新增多少条 `monitoring_citations` |
| 未跑完的格 | 明确列出来，别含糊成"失败" |

`GET /monitoring/diagnostics` 可以直接看失败分布，不用自己数。

## 四、复核交接（跑完立刻做，别拖）

引用跑出来是**全部 `auto`**，而看板的引用率只数 `manual_confirmed`——不复核，三个数就是 0。


## 五、验收清单

- [ ] 基线轮次 `is_baseline=true`，且只有这一个
- [ ] 任务数 = 6 × 4 = 24（不是 30，也不是 6）
- [ ] 每格状态是 `hit` / `miss` / `failed` 三者之一，没有 `pending`
- [ ] 失败格都带 `failure_code`
- [ ] 任意抽 3 格：`GET /monitoring/traces/{trace_id}` 能追到原回答与引用 URL
- [ ] 引用已分批复核，`citation_rate` 出数（或明确写"本轮确实无引用"）

## 六、不要做的事

- ❌ 不要改历史样本的状态来凑数
- ❌ 不要把 `failed` 改成 `hit`/`miss`（失败是可解释的，伪造不是）
- ❌ 不要回写 `review_status='auto'`（接口会直接拒绝）
- ❌ 不要为某一格反复重跑直到"看起来成功"——同一格多次尝试要落成 `sampling_no` 递增，不是覆盖
