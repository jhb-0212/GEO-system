# 发布可见性检测（2026-11-17）

把「发布 → 回执 → **被搜索收录** → 被 AI 引用」里原先空着的那一层补上：对每条发布回执，查它的页面能不能被搜索引擎检索到。

只做诊断，**不参与渠道归因**。渠道效果仍然只看「引用 URL 精确命中回执 URL」。

## 1｜为什么要这一层

之前的口径能回答两个问题：

- `monitoring_citations.channel_id`：AI 引用里有多少条命中了我们的发布回执（渠道效果）；
- `stats.sources`：AI 从哪些域名取证（信源分布）。

中间缺一环：**我们发出去的页面，到底有没有进搜索索引**。缺了这层，「渠道发了没效果」只能笼统归因，无法区分：

| 现象 | 真实原因 | 该做什么 |
|---|---|---|
| 回执有，引用 0 条 | 页面没被收录 | 换渠道 / 换发布方式 / 检查是否被屏蔽 |
| 回执有，页面已收录，引用 0 条 | 收录了但 AI 没引 | 改内容、改选题、换 AI 平台 |
| 回执有，页面已收录，引用有 | 正常 | 复制这类打法 |

## 2｜检测机制

一条回执的检测流程：

1. **取标题**：`publish_receipts.task_id → publish_tasks.version_id → content_versions.item_id → content_items.title`，链路断在哪一环就退回 URL 末段；
2. **构造 query**：标题按千帆口径截断——`messages.content` 上限 72 字符且**一个汉字算两个字符**（`truncate_to_weight`）；
3. **限定站点**：用回执 URL 的主机（去 `www.`）做 `search_filter.match.site`，避免全网噪声；
4. **限速与重试**：客户端自己保证两次上游调用间隔 ≥0.6 秒（全局锁，跨项目共用同一账号配额）；429 只对 `RATE_LIMIT_*`（QPS 类）退避重试 2 次——`QUOTA_USER_DAILY_FREE`、`BILLING_INSUFFICIENT_BALANCE` 重试也是同样结果，直接记失败，不白等；
5. **判定命中**：只认返回 `references[].url` 与回执 URL **`url_key` 归一后完全相等**（复用 `citation_attribution.url_key`：忽略 scheme、去 `www.`、去末尾斜杠、剔 `utm_`/`gclid`/`spm` 等跟踪参数，保留其余 query）；命中取第一次出现的序号做 `position`；
6. **失败留痕**：上游报错（超时、429、鉴权、200 但带 `code`）写 `error_code`，`matched` 保持 false——**不能读成"没收录"**。查询词为空时直接返回 `empty_query`，不发起调用（上游对空串不报错，只会返回一堆无关结果）。

## 3｜落表

`publish_visibility_checks`（迁移 `ea55a9ad6c5d`），只追加不改历史，便于看"收录延迟"：

| 字段 | 说明 |
|---|---|

| `matched_url` | 命中的实际 URL（可能与回执 URL 有跟踪参数差异） |

| `site` | 限定的站点 |

| `error_code` | 非空表示没查成：`RATE_LIMIT_SEARCH_QPS` / `QUOTA_USER_DAILY_FREE` / `InvalidArgument` / `216003`（鉴权） / `timeout` / `unreachable` / `invalid_json` / `no_references` / `empty_query` |

## 4｜怎么跑

凭据：环境变量 `QIANFAN_API_KEY`（`.env` 已配，不入库、不打印）。

```powershell
# 预演，不写库
backend\.venv\Scripts\python.exe backend\scripts\check_publish_visibility.py --project-code gz-base --dry-run

# 正式检测并写库
backend\.venv\Scripts\python.exe backend\scripts\check_publish_visibility.py --project-code gz-base

# 只查指定回执
backend\.venv\Scripts\python.exe backend\scripts\check_publish_visibility.py --receipt-id <uuid>
```

接口：`GET /api/v1/projects/{project_id}/stats/publish-visibility?limit=50`（权限 `stats.read`）。
手工触发：`POST /api/v1/projects/{project_id}/stats/publish-visibility/check`（权限 `monitoring.execute`，body `{"limit": 20}`，1–50），返回本次汇总 `{checked, matched, unmatched, failed}`；同项目 **60 秒节流**，连点返回 429 `too_many_requests`，避免重复烧免费额度；缺 `QIANFAN_API_KEY` 返回 409 `credential_missing`。每次触发写审计（`stats.publish_visibility.check`）。
页面：工作台 → 统计看板 → **发布可见性**（与「信源分布」一样单独请求、单独降级，外部搜索超时不拖垮整页）；有 `monitoring.execute` 的账号在面板右上能看到「立即检测（20 条）」，点击后显示汇总提示并自动刷新列表。

### 5.1｜搜索能力审查复测（同日）

| 场景 | 结果 |
|---|---|
| 成功响应结构 | 只有 `references` + `request_id`，**没有 `code` 字段** → 不会把成功误判成失败 |
| `site` 过滤是否生效 | `site=k.sina.com.cn` 搜「广州」，5 条结果 **5/5** 都在该主机 |
| 429 的 body | `{"code": "RATE_LIMIT_SEARCH_QPS"}`，被正确写进 `error_code` |
| 429 触发条件 | **8 并发 → 5 次 429**；串行 8 次全成功、平均 0.59s/次 ≈ 1.7 QPS，已贴近限流线 |
| 超长 query（权重 80，超 72） | 上游仍返回 200 + 结果 → 说明我们按 72 截断是**保守**做法，不是硬限制 |
| 空 query（`content=""`） | 上游返回 **200 + 无关结果**，不报错 → 必须客户端前置拦截 |
| 坏 key | 401 + `{"code": 216003, "requestId": ...}` → 上游码用 `code`（int）、request_id 用驼峰 |

审查结论：判定口径（URL 精确相等 / `site` 归属 / 失败不入"未收录"）成立；真问题是**批量检测没有限速与退避**，已被本轮修复覆盖。

## 6｜已知限制

1. **72 字符截断**：长标题只能取前 72（汉字算 2）。标题过短的页面可能召回不准，此时 `matched=false` 未必等于"没收录"——解读时看 `result_count` 是否为 0。
2. **`site` 过滤是付费功能（目前限免）**：如果将来收费或关闭，检测会退化成全网搜索，命中率下降。
3. **配额按天发**：每月 1500 次平摊到每天约 50 次。当前量级（1 条回执）完全够；回执上千后需要分批跑。
4. **索引延迟**：刚发布的页面通常要等一段时间才进索引，所以应**按天重复检测**看趋势，不要只看一次结果。
5. **反向不可靠**：`matched=true` 只说明"能搜到"，不能反推"AI 一定会引"；`matched=false` 也不能证明"内容被降权"。
6. **上游 QPS 很紧**：实测 8 并发会打 5 个 429、串行 0.59s/次已贴近限流线。客户端已限速 0.6s/次并对 QPS 类 429 退避重试 2 次，但回执量大（一次 >50 条）时建议分批并错开时间，别和别的调用共享同一分钟窗口。
7. **`position` 是"本次返回列表的第几条"**，不是搜索引擎排名。搜索引擎按相关性排序且每次可能不同，所以只用于判断"大概在前几"，不能当排名指标。
