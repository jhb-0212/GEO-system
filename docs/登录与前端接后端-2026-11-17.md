# 登录与前端接后端（2026-11-17）

> 起因：《GEO执行计划-详细对账_2026-11-17》第 2.2 节与第 7 节写着「`auth/login` 未实现（现靠 `dev_token.py` 顶替）」「前端 Next.js 骨架，未接后端」。本文先核实这两条是否成立，再补真实缺口。

## 1｜核实结果：两条断言都不成立

| 对账文档的写法          | 仓库实际           | 证据                                                                                                                                                                                                                                    |
| ---------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth/login` 未实现 | 已实现，且带失败限流与锁定  | `backend/app/api/auth.py`：`POST /login`（`login_throttle` 限流 + 触达阈值写 `auth.login_locked` 审计）、`GET /me`（返回用户与项目/角色/能力码）、`POST /password`（改密后 `token_version += 1` 让旧令牌立即失效）                                                             |
| 前端骨架未接后端         | 已接，且是单点 BFF 转发 | `frontend/app/login/page.tsx` → `POST /internal/session` → 后端 `/api/v1/auth/login`，令牌写 httpOnly cookie（`geo_workbench_session`，8 小时）；业务读写在 `frontend/app/internal/workbench/data/route.ts` 一个路由里转发 30 多个资源（GET/POST/PUT/PATCH/DELETE） |
| ——               | 会话失效会自动跳登录     | `frontend/lib/workbench/client.ts`：401 或 `token_expired/token_invalid/token_stale/user_inactive` → 清 cookie + `location.replace("/login")`                                                                                            |

E2E 也证明这一层是通的：`workbench-read.spec.ts` 4 个用例真实登录三种角色跑真实后端（`4 passed`），不是 mock。

**结论**：这两条是旧信息（同一份文档还把「4 引擎只有元宝调通」写成结论，见附录，与实测相反）。真正缺的不是「有没有」，而是**改密没有前端入口**。

## 2｜补的缺口：修改密码入口

后端有 `POST /api/v1/auth/password`，前端此前完全没有入口（账号菜单只有「切换账号」「退出登录」）。补了三层：

| 层   | 文件                                                    | 做法                                                                                                                                |
| --- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| BFF | `frontend/app/internal/session/password/route.ts`（新增） | 读会话 cookie → 转后端 `/auth/password` → **用响应里的新 token 覆盖 cookie**。后端改密会 `token_version += 1`，旧 token 立即失效；不写回新 token 的话，用户改完密码会把自己登出 |
| 客户端 | `frontend/lib/workbench/client.ts`                    | `changePassword(current, next)`，错误码与文案沿用已有 `WorkbenchApiError`                                                                    |
| 页面  | `frontend/components/workbench-app.tsx`               | 账号菜单新增「修改密码」；弹窗含原密码 / 新密码 / 确认新密码，前端先校验（≥8 位、两次一致、不得与原密码相同），失败展示后端原文（如「原密码错误」）                                                    |

## 5｜系统管理员两个动作

能力码表（28 个）里没有 `user.manage` / `system.admin`，因此两个端点只认 `is_system_admin`，非系统管理员返回 403 `system_admin_only`。

**后端**

| 端点 | 行为 |
|---|---|
| `POST /api/v1/system/users/{user_id}/reset-password` | 行锁取用户 → 404 `user_not_found` / 400 `user_inactive` → 置新 hash + `token_version += 1`（旧令牌立刻失效）→ 审计 `auth.password_reset` |
| `POST /api/v1/system/login-throttle/reset` | 带 `client_ip` 时清该账号 + 该 IP 的 4 个窗口键；不带时按账号解封，清该账号窗口键与它最近失败来源 IP 的窗口键；审计 `auth.throttle_reset` 记录 `client_ip` / `cleared_keys` / `operator` |

限流的实现事实：`LoginThrottle`（`backend/app/services/login_guard.py`）是 Redis 计数窗口（分钟 5 次 / 小时 20 次，TLL 2 小时），**不存在持久锁号**，所以「人工解锁」本质是清窗口计数。管理员通常不知道用户 IP，因此新增 `_ips_key()` 记录该账号失败来源的**IP 摘要集合**（只存 sha256 摘要，不落明文），`reset_username()` 据此只凭账号名即可解封。

**前端**

| 层 | 文件 | 做法 |
|---|---|---|
| BFF | `frontend/app/internal/workbench/system/route.ts` | `kind=reset-password` / `kind=throttle-reset`，校验 uuid 与 8–128 位密码；未登录 401、mock 模式 400 |
| 客户端 | `frontend/lib/workbench/client.ts` | `resetUserPassword`、`resetLoginThrottle` |
| 成员管理 | `frontend/components/members-workspace.tsx` | 成员行「重置密码」，弹窗 `RESET PASSWORD`，成功后提示其他设备登录已失效 |
| 内部排障 | `frontend/components/diagnostics-workspace.tsx` | 新增「解除登录限流」面板：账号必填、来源 IP 可留空（留空按账号解封全部来源） |

**元宝那次为什么报未配置（结论已修正）**：`.env` 两个 key 都在，当时进程里跑到的是改之前的 `os.getenv("YUANBAO_SECRET_KEY")`——pydantic-settings 读 `.env` 不导出到 `os.environ`，所以读不到。并行工作流其实早已把该处改成 `read_credential_env(SECRET_KEY_ENV)`（同时改了 TC3 签名：`("TC3" + secret_key)`、`x-tc-action` 不参与签名、`body_payload` 去掉 `Cnt`、补 `answer_kind: "search_result"`），**根因是后端进程没热重载、还在跑旧代码**。重启后端后立刻 `success=True, 429.2 ms`，四个引擎全绿；随后用 `PATCH .../entries/{entry_id}` 把元宝入口由停用改启用，`ai_engine_entries.is_active=true`。

重启后四引擎全量复测：deepseek `True 875.4ms`、doubao `True 2724.9ms`、wenxin `True 2302.7ms`（2026-11-17 改为 ERNIE 对话模型后）、yuanbao `True 203.4ms`。
